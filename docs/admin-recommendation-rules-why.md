# Recommendation rules — зачем эти ручки (для чайников)

Админка rules — это не «настройки красоты». Это **если → то** для рекомендаций после анкеты: когда что предлагать и что говорить.

Файл с правилами: `apps/server/data/recommendation-rules.json`.  
Технический справочник ручек: [admin-recommendation-rules.md](./admin-recommendation-rules.md).  
Глоссарий всех имён (Field, Operator, слоты, DS, Profile): [admin-glossary.md](./admin-glossary.md).

---

## Зачем вообще правила

Клиент ответил на вопросы (и иногда кликал по вариантам). Система должна:

1. понять, **что уже известно**;
2. предложить **подходящий модуль/вариант**;
3. при конфликте — **спросить словами**, а не молча выбрать «наугад».

Каждая карточка = одно такое правило. Несколько правил = политика «сначала важное, потом запасное».

---

## Зачем ручки на списке

| Ручка | Зачем |
|---|---|
| **+ Add rule** | Добавить новую политику («если X — сделай Y»), которой ещё нет. |
| **Delete** | Убрать правило, которое больше не нужно. Без Save удаление не закрепится на диске. |
| **Свернуть / раскрыть** | Не смотреть сразу все поля — меньше шума, открыл только нужное. |

---

## Meta — «кто это правило»

| Ручка | Зачем простыми словами |
|---|---|
| **Rule id** | Имя правила, чтобы отличать в файле и логах («это то про бюджет» vs «то про детей»). |
| **Priority** | Очередь. Меньше число = важнее. Сначала строгие/особые случаи, в конце — «по умолчанию». |
| **Condition kind** | Как писать условие: всегда / одно условие / все сразу (AND) / любое из (OR). |
| **Active** | Выключатель. Выкл. = правило лежит в файле, но движок его игнорирует. Удобно «выключить на время», не удаляя. |

## When — «когда срабатывает»

Это фильтр: **при каких ответах/состоянии клиента правило имеет смысл**.

| Ручка | Зачем |
|---|---|
| **Field** | *На что смотрим*: бюджет, материал фасада, есть ли дети, фаза анкеты, куда человек смотрел в UI… |
| **Operator** | *Как сравниваем*: равно / не равно / больше / «поле заполнено» (`exists`) и т.д. |
| **Value** | *С чем сравниваем*: например `yes`, `durable`, число бюджета. |
| **Add / Remove condition** | Собрать сложное условие из нескольких простых (до 3), не плодя отдельные карточки. |

**Зачем kind `always`:** запасной вариант «если ничего особенного не подошло».  
**Зачем `allOf`:** «и то, и другое» (дети **и** выбран материал).  
**Зачем `anyOf`:** «хотя бы что-то из списка уже известно» (бюджет **или** стиль **или** материал).

Без нормального When правило либо никогда не сработает, либо будет срабатывать слишком часто.

## Then — «что сделать, если When сработал»

Два разных мира (важно по инварианту проекта):

### `filterCatalog` — про конфигурацию

| Ручка | Зачем |
|---|---|
| **Filter key / value** | Сузить каталог: конкретный SKU, категория шкафа, отделка, или «бери предпочтения из ответов» (`preferFrom: known`). |

Смысл: **подобрать железку/модуль** под ситуацию, а не просто красиво написать.

### `triggerDialogueAction` — про речь

| Ручка | Зачем |
|---|---|
| **Topic** | Какую реплику/тему диалога включить (например конфликт взгляда и ответа → предложить как альтернативу). |

Смысл: **поговорить**, не меняя молча план. Конфиг по-прежнему только через совместимость/BOM, не «из текста LLM».

## Save — зачем отдельная кнопка

Пока крутишь ручки — черновик в браузере.  
**Save** = записать на диск и в память сервера, чтобы после F5 / рестарта правила остались.

---

## Как думать одной фразой

> **When** = «в какой ситуации клиент».  
> **Then** = «что тогда делать: подобрать из каталога или сказать фразу».  
> **Priority / Active** = «в каком порядке и включено ли это».

Mandatory-тройка в seed как раз такая политика: сначала явные ответы, потом конфликт поведения, в конце дефолт `BASE-600`.
